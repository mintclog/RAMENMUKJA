상태: 2026-10-17 제품 흐름 구현 및 로컬 검증 단계. 외부 프로젝트 미생성·운영 DB 미적용·실제 인증 메일/지도/Storage/탈퇴·원격 배포 미검증. 아래 10~13절은 이전 코드·문서 작업 기록이다.

## 1. 현재 구현과 연결 상태

| 영역 | 코드에서 제공하는 동작 | 남은 실제 연결 검증 |
|---|---|---|
| 인증·프로필 | 이메일 가입·로그인·인증·재발송·비밀번호 재설정, 자동 생성·변경 가능한 닉네임, HttpOnly 쿠키 | Supabase Email 확인·SMTP·템플릿·실제 메일 수신 |
| 메뉴·리뷰 | 가게 → 동일 크기 메뉴 선택/추가 → 사진 이어받기 → 리뷰 작성/기존 리뷰 수정, 주문 옵션, 국물·면·고명 펼치기 | 실제 DB·Storage·권한·다중 사용자 |
| 좋아요·대표 사진 | 회원당 리뷰별 1회/취소, 본인 제외, 동률은 작성순/첫 사진, 사진 없으면 회색 | 실제 API·Storage·집계 |
| 등록·초안·운영 | 주소·좌표 요청, 승인/반려/중복 가게 연결, 비공개 초안, 승인 후 작성자 발행. 메뉴+리뷰 발행은 DB 트랜잭션, 기존 리뷰 충돌 시 초안 비교 | 실제 운영 계정·알림·초안 보관기간 |
| 탈퇴 | 비밀번호 재확인, 개인 저장 삭제·공용 메뉴 유지, 삭제 또는 비공개 보존 점검, 작성자 정보 분리·Auth 계정 삭제 | 서버 전용 관리 키와 실제 Storage 복사/정리·개인정보 점검·재시도 |
| 지도 | Maps JavaScript API 핀·선택, PC 목록 병렬/모바일 전환, 가게 길찾기, 클릭으로 등록 위치 선택 | Google Cloud 키·지도 ID·결제·도메인/API 제한 |

체험 모드는 브라우저 저장이며 인증·운영 승인·원격 동기화가 아니다. 가상 가게를 실제 지도에 표시하지 않는다. 운영 설정이 없으면 Vercel에서는 체험 데이터로 전환하지 않는다. 기존 체험 기록을 공용 DB에 자동 전송하지 않는다.

## 2. 사용자 계정과 프로젝트 생성

다음 계정 생성·약관 동의·결제 정보 입력은 계정 소유자가 직접 진행한다. 유료 플랜 선택은 필요 용량·트래픽을 확인한 뒤 별도 결정한다.

1. [Supabase Dashboard](https://supabase.com/dashboard)에서 새 프로젝트를 만든다. 처리 지역을 확인하고 기록한다.
2. [Google Cloud Console](https://console.cloud.google.com/)에서 지도용 프로젝트를 만들고 Maps JavaScript API와 결제를 설정한다. API key에는 운영 도메인과 사용 API 제한을 적용하고 사용량·비용을 확인한다. 주소 검색·좌표 변환용 추가 API는 별도 선택 사항이다.
3. [Vercel Dashboard](https://vercel.com/dashboard)에서 이 소스의 프로젝트를 생성한다.

비밀 키를 채팅·문서·Git에 넣지 않는다. 메일 공급자 인증 정보는 Supabase의 SMTP 설정에서 관리한다. 계정 탈퇴에만 서버 전용 Supabase `service_role` 키를 사용한다. 브라우저·상태 API·로그·문서에 실제 값을 노출하지 않는다. 키가 없으면 탈퇴는 준비 상태로 표시하고 데이터를 변경하지 않는다. 지도 key의 클라이언트 제공 방식과 설정 이름은 후속 구현에서 정하며, 브라우저용 key도 도메인·API 제한이 필요하다.

## 3. DB와 사진 저장소

새 테스트 프로젝트에서 [초기 SQL](../supabase/migrations/202610160001_initial.sql) → [추가 마이그레이션](../supabase/migrations/202610170002_product_flows.sql) 순서로 적용한다. 초기 SQL이 이미 적용된 DB에는 두 번째만 적용한다. 추가 SQL은 프로필·좋아요·비공개 초안·탈퇴 작업, 리뷰 옵션과 개인정보 점검 상태, 가게 승인/반려 및 서버 권한 함수를 추가한다. 과거 리뷰의 취향·협찬 필드는 호환성을 위해 남기지만 새 API·화면에서는 사용하지 않는다. 기존 데이터 백업과 변경 영향을 확인한 뒤 적용한다. 이름이 같은 테이블이 있는 프로젝트에 그대로 적용하지 않는다. 전체 SQL은 트랜잭션으로 실행되며 기존 테이블을 삭제하는 문장은 없다.

생성 대상: 가게, 메뉴, 리뷰, 저장, 동의 기록, 신고, 등록 요청, 공개 집계 view, 관리자 조치 함수, RLS 및 비공개 사진 버킷.

적용 후 최소 검증:

- 비회원은 공개 메뉴·공개 리뷰만 읽을 수 있어야 한다.
- 서로 다른 두 회원은 상대방의 리뷰·저장·사진을 변경할 수 없어야 한다.
- 일반 회원은 `hidden`, `user_id`, 관리자 역할·운영 데이터를 바꿀 수 없어야 한다.
- 숨긴 리뷰·사진은 비회원에게 보이지 않고 점수에서도 제외되어야 한다.
- 이메일 인증을 마친 회원만 자신의 가게 등록 요청을 제출하고 결과를 확인할 수 있어야 한다.
- 관리자만 신고 처리·리뷰 숨김·가게 등록 승인/반려를 할 수 있어야 한다. 승인 전 가게 요청은 공개 가게 목록과 지도에 노출되지 않아야 한다.
- 이메일 인증을 마친 회원은 공개 가게에 메뉴를 추가할 수 있어야 하며 관리자 승인 없이 즉시 공개되어야 한다. 일반 사용자의 메뉴 이름 변경·삭제는 허용하지 않는다.
- 같은 회원·같은 메뉴의 리뷰는 서버·DB에서도 하나로 유지해야 한다. 재평가 시 기존 리뷰 수정으로 처리하고 동시 요청으로 리뷰가 중복 생성되지 않는지 확인한다.

이 조건은 모의 API 테스트만으로 검증되지 않으므로 실제 DB에서 확인하기 전 공개 운영을 완료로 판단하지 않는다.

## 4. Vercel 환경 변수

Vercel 프로젝트의 Settings → Environment Variables에 설정한다. 이 작업에서는 `.env`를 읽거나 작성하지 않았다.

| 이름 | 내용 |
|---|---|
| `APP_ORIGIN` | 최종 HTTPS 사이트 주소. 끝의 `/`는 생략 |
| `SUPABASE_URL` | 프로젝트 API URL |
| `SUPABASE_ANON_KEY` | 프로젝트의 legacy `anon` JWT API key. `service_role` 또는 secret key를 넣지 않음 |
| `PUBLIC_OPERATOR_NAME` | 실제 운영자·개인정보 문의 담당 명칭 |
| `PUBLIC_CONTACT_EMAIL` | 실제로 접수 가능한 문의 이메일 |
| `PUBLIC_OPERATOR_ADDRESS` | 운영자 주소 |
| `PUBLIC_DATA_REGION` | 실제 저장·처리 지역과 외부 이전 대상·목적·시기·방법·기간·거부 관련 안내. Vercel·Supabase의 실제 설정과 계약을 확인해 작성 |
| `PUBLIC_RETENTION_POLICY` | 항목별 보관기간·삭제 방법·법정 보관 예외·백업 소거 기준 등 실제 운영 정책 |
| `ALLOW_PUBLIC_SIGNIN` | 운영 정책·메일·DB 검증 후 이메일 가입·로그인·인증 메일 처리를 열 때만 `true` |
| `SUPABASE_SERVICE_ROLE_KEY` | 탈퇴 시 사진 복사·정리와 Auth 사용자 삭제에만 쓰는 서버 비밀 키. 클라이언트에 제공하지 않음 |
| `GOOGLE_MAPS_API_KEY` | Maps JavaScript API용 브라우저 키. 운영 도메인과 사용 API를 제한 |
| `GOOGLE_MAPS_MAP_ID` | Google Cloud에서 만든 JavaScript 지도 ID |

`PUBLIC_` 값은 정책 화면에 공개되므로 개인 비밀 정보·키를 넣지 않는다. 운영 정보의 존재를 코드가 검사하지만, 내용의 법적 충족 여부까지 자동 검증하지는 않는다.

## 5. 이메일·비밀번호 인증과 Google Maps

1. Supabase Auth에서 이메일·비밀번호 인증과 이메일 확인을 설정한다. 가입 화면은 이메일·비밀번호와 자동 생성 후 수정 가능한 닉네임을 제공하고 약관 동의·만 14세 이상 확인을 구분한다.
2. 운영용 SMTP 공급자와 발신 주소를 설정하고 가입 확인·재발송·비밀번호 재설정 메일을 실제 수신함에서 확인한다. 발송 제한과 반복 요청 방지를 확인한다.
3. Site URL을 APP_ORIGIN과 맞춘다. 이메일 인증 및 비밀번호 재설정의 실제 구현 경로를 정한 뒤 필요한 Redirect URLs만 허용한다. 실제 복귀 화면은 `/login?mode=verify`다.
4. 이메일 미인증 계정은 리뷰·저장·신고·가게 등록 요청·메뉴 추가를 수행할 수 없도록 서버에서도 검증한다. 비밀번호는 Supabase Auth가 처리하고 앱 DB·로그에 저장하지 않는다. 공개 프로필에 이메일을 노출하지 않는다.
5. 가입 → 인증 메일 → 인증 완료 → 로그인 → 원래 화면 복귀 → 로그아웃, 재발송·만료 링크·재설정·오류 복구를 실제 계정으로 확인한다.
6. 가입 확인 메일 템플릿의 링크를 `{{ .SiteURL }}/login?mode=verify&type=signup&token_hash={{ .TokenHash }}`, 재설정 메일 링크를 `{{ .SiteURL }}/login?mode=verify&type=recovery&token_hash={{ .TokenHash }}`로 설정한다. 메일 스캐너가 단순 방문만으로 토큰을 소비하지 않도록 확인 화면에서 POST로 검증한다. 사용하지 않는 소셜 인증 공급자를 비활성화한다. 비밀번호는 현재 구현에서 12~128자로 검증하며 Supabase의 비밀번호 정책과 맞춘다.

Google Maps는 사용자가 직접 요청하고 관리자가 승인한 가게의 좌표만 표시한다. 등록 시 가게 이름·주소·지도 위치를 확인하고 중복 후보를 검토한다. Places 자동 수집·일괄 등록은 하지 않는다. 지도 제공자 표시를 유지하고 외부 길찾기와 실패 안내를 검증한다.

운영 정책 화면은 이메일·닉네임·주문 옵션·좋아요·초안·Google Maps·탈퇴 처리 항목에 맞춰 갱신했다. 실제 운영자·SMTP 공급자·처리 지역·보관기간과 대조한 후 공개한다. 지도 SDK를 위해 CSP에 Google 지도 도메인과 인라인 스타일을 허용했으며 스크립트는 지정 도메인으로 제한한다.

## 6. 빌드와 배포

```sh
npm test
npm run check
node --check server/api.mjs
node --check server/photos.mjs
node --check src/service.js
node --check src/live-legal.js
node scripts/build.mjs
```

Vercel은 [vercel.json](../vercel.json)에 따라 정적 앱을 `dist`로 복사하고 API 함수를 별도 배포한다. 정적 출력에는 `index.html`과 `src`만 포함한다. 문서·SQL·서버 소스는 정적 공개 폴더에 넣지 않는다.

기존 `npm start` / `npm run dev` / `시작.bat` 로컬 실행은 유지된다. 로컬에서 실서비스 연결을 검증할 경우 환경 변수는 사용자가 안전한 방식으로 런타임에 공급하고, 테스트용 프로젝트와 운영 프로젝트를 구분한다.

## 7. 초기 운영자와 실데이터

최초 운영자도 이메일·비밀번호로 가입하고 이메일 인증을 완료한 뒤, Supabase의 관리 권한으로 해당 Auth 사용자에게 `app_metadata.role = admin`을 부여한다. 운영자 본인의 정확한 사용자 ID를 확인하고 기존 metadata를 보존한다. `user_metadata`로 권한을 주면 안 된다. 역할 적용 후 다시 로그인한다.

회원의 직접 등록 요청을 운영 관리(`/admin`)에서 검토한다. 가게 이름·주소·지도 위치와 중복 여부를 확인하고 승인한 가게만 공개하며 반려 사유를 요청자에게 안내한다. 공개된 가게의 메뉴는 인증 회원이 리뷰 작성 중 직접 추가하며 관리자 승인 없이 즉시 공개한다. 미등록 가게의 메뉴·리뷰는 비공개 초안이며 가게 승인 후 작성자가 발행한다. 정보 출처와 사진 사용 권한을 확인하고 가상 샘플 데이터를 운영 DB에 자동 복제하지 않는다. 신고·요청 검토 후 처리 완료, 리뷰 숨김·복원, 판매 종료·재개를 확인한다.

## 8. 공개 전 남은 검증

- 실제 Supabase 마이그레이션, RLS·Storage 소유권·권한 검증.
- 이메일·비밀번호 가입, 인증·재발송·비밀번호 재설정·로그인·갱신·로그아웃, 서로 다른 두 계정의 리뷰·저장 흐름.
- 가게 직접 등록 요청·중복/위치 검토·승인/반려·결과 확인, 승인 가게만 공개 목록과 Google Maps에 노출되는지 확인.
- Google Maps 도메인·API key 제한·결제/사용량, 지도 표시·외부 길찾기·연결 실패 복구.
- Vercel 배포 및 API 동작, 도메인·쿠키·callback 주소 일치.
- 가게 페이지 → 메뉴 선택/등록 → 리뷰 작성. 동일 크기 메뉴 추가 카드, 메뉴명·가격·장르·사진 필수·기존 메뉴 중복 안내, 즉시 공개·선택 유지.
- 일반 사용자 공용 메뉴 이름 변경·삭제 차단, 자동 생성 닉네임의 가입 시/가입 후 수정.
- 취향·협찬 입력 제거, 국물·면·고명 접기/펼치기, 특제·곱빼기·추가 토핑 리뷰 표기, 메뉴 등록 사진을 리뷰 사진으로 이어받기.
- 리뷰 좋아요와 대표 사진 선정·후보 삭제/숨김 재선정, 회색 사진 없음 상태. 인증 회원 1회/취소·본인 제외·동률 작성순/첫 사진 기준을 검사.
- 평점순 결과 없음의 ‘평가 수 조건을 해제하고 보기’, 다른 조건 보존.
